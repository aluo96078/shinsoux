# ADR-0004（草案）：內建翻譯模組

狀態：階段 1 已實作並隨 v1.0.2-beta.1 發佈（見 §9）；其餘分期尚未實作。階段 0（引擎可行性驗證）的結果見 §3。
日期：2026-11-14

## 1. 目標與範圍

讓使用者在閱讀器內翻譯小說與漫畫。

- 內建免費、完全離線的機器翻譯，不需要任何金鑰。多數使用者不會付費，所以這是第一優先。
- 願意付費的使用者可以填自己的 AI 模型金鑰或翻譯平台金鑰，換取較好的品質。
- 翻譯過的內容留存，不重複計算，也不重複計費。

不做的事：

- 不提供官方代管的翻譯服務，App 不內建任何付費金鑰。
- 不把原文或譯文上傳到專案方的任何伺服器。
- 不使用非官方的免費網頁翻譯端點（違反對方條款、隨時可能失效，而且會把閱讀內容外送）。
- 漫畫不做去字重繪，只做覆蓋式顯示。
- 離線引擎不保證中日韓英以外的來源語言；那些語言靠自備金鑰的供應商。

## 2. 已定案的決定

已定案：

| 項目 | 決定 |
| --- | --- |
| 優先順序 | 離線機翻放第一階段，自備金鑰放第二階段 |
| 離線引擎 | Mozilla 的 Firefox 翻譯引擎（bergamot-translator，底層 Marian）與其模型 |
| 第一批語言 | 繁體中文、簡體中文、日文、韓文、英文 |
| 小說先於漫畫 | 漫畫需要文字辨識，難度高一個量級 |

同日定案的三項：

| 項目 | 決定 |
| --- | --- |
| 譯文是否進備份 | 由使用者選擇。備份時可分別勾選「付費取得的譯文」與「免費機翻的譯文」，見 §4.2 |
| 漫畫的承諾範圍 | 只承諾到階段 3（自備金鑰的漫畫翻譯）；階段 4 的免費選項視實測結果，不承諾 |
| 中日韓英以外的來源語言 | 只靠自備金鑰的供應商，離線引擎不保證 |

## 3. 階段 0：可行性驗證結果

驗證用的檔案在本機的 `spikes/translation-poc/`（不在版本庫內）。引擎原始碼取自
`github.com/mozilla/translations` 的 `8eada03`，模型取自 Firefox 的模型登錄表並以 SHA-256 驗證。

### 3.1 授權

- 引擎與模型都是 MPL-2.0，可以隨 App 散布。採用時要列入 `THIRD_PARTY_NOTICES.md`。
- 不採用 NLLB：權重是 CC-BY-NC（非商用），會讓下游使用者有授權風險。

### 3.2 語言與模型

- 登錄表目前有 60 種語言，全部以英文為中介，沒有任何不經英文的語言對。
- 繁中、簡中、日文、韓文都有雙向模型（各自對英文）。
- 每個方向約 50 MB（模型約 44 MB，加上詞表與短名單）。日文翻繁中需要兩個方向，約 105 MB。

### 3.3 建置

| 平台 | 結果 |
| --- | --- |
| macOS arm64 | 可建置並執行 |
| Android arm64（NDK 27） | 可建置，在實機執行 |
| iOS arm64（最低 iOS 16） | 可建置，在模擬器與實機執行 |
| Windows | 未驗證 |

需要自行維護的修補：

- 引擎原始碼 5 處，才能用新版 Xcode 編譯（zlib 的 `fdopen` 巨集、sentencepiece 的一個
  `constexpr`、關閉「警告視為錯誤」、`simd_utils.h` 缺少 `<fenv.h>`、ARM 的編譯定義要全域傳入）。
- 建置設定 3 處：內附的 PCRE2 要加上新版 CMake 的相容參數並關閉 JIT；iOS 要明確指定處理器，
  否則 cpuinfo 連結失敗；iOS 交叉編譯要自行提供執行緒與試編譯設定。

### 3.4 效能（一章約 2.4 萬字日文，單執行緒）

| 裝置 | 日→英 | 英→繁中 | 單一模型記憶體峰值 |
| --- | --- | --- | --- |
| Android SM-S9280（Android 17） | 2.7 秒 | 2.6 秒 | 約 340 MB |
| iPhone 17 Pro Max（iOS 27.0.1） | 2.27 秒 | 2.18 秒 | 約 356 MB |
| macOS（M 系列） | 2.3 秒 | 2.2 秒 | 約 380 MB |

- 載入一個模型不到 0.1 秒；5 行短文每段約 0.1 秒。
- 多執行緒只快三到四成，記憶體卻超過兩倍（iPhone 雙執行緒峰值超過 1 GB，Android 四執行緒
  837 MB）。手機上使用單執行緒。
- 模型載入後不會自動釋放：iPhone 上連續載入四次，佔用升到 908 MB，翻譯服務結束才降回
  13 MB。整合時必須主動管理模型的生命週期。
- 以上都是旗艦機。中低階手機會慢幾倍，記憶體需求不會變小；這部分未驗證。

### 3.5 品質（日→英→繁中）

- 敘述句大致可讀。
- 對白常錯譯，有時意思相反（「お前には指一本触れさせない」譯成「我就不讓你碰一根手指」）。
- 人名不穩定：同一個「葵」在相鄰句子被譯成「艾伊」「艾歐」「葵」。
- 漫畫短句效果差（「お兄ちゃん、だいすき！」譯成「哥哥,很好!」）。
- 標點是半形，需要後處理。

定位：免費、看得懂劇情。不是文學品質，介面上要明確標示為機器翻譯。

## 4. 架構

四個部分，前兩個與引擎無關，所有供應商共用。

### 4.1 供應商層

- 統一介面：輸入一批段落與語言對，輸出譯文（可串流）、用量與錯誤分類。
- 介面在階段 1 就定好，先只接離線引擎；階段 2 加雲端供應商時不改閱讀器與留存層。
- 預定的實作：
  - 離線引擎（階段 1）。
  - OpenAI 相容端點：填 base URL、金鑰、模型名稱，一個實作涵蓋 OpenAI、DeepSeek、
    OpenRouter、本機 Ollama（階段 2）。
  - 翻譯平台：先做 DeepL（階段 2），再視需求加 Google Cloud、Azure。
  - Anthropic、Gemini 的原生格式（之後）。
- 使用者可設定多個供應商並排序，失敗時依序退回。

### 4.2 翻譯記憶（留存層）

以內容為鍵，不以章節 ID 為鍵。

- **段落級**：鍵為「原文段落雜湊＋來源語言＋目標語言＋引擎識別（供應商、模型、版本）＋譯名表
  版本」。章節重新下載、換來源或來源站改稿時，只有變動的段落需要重翻；同一部作品在不同來源的
  相同段落可以共用。
- **中間結果**：兩段式翻譯的中間英文也留存。日→英做過一次後，要翻成繁中或簡中都不必重跑
  前半段。
- **章節清單**：鍵為「作品識別＋章節識別＋原文內容雜湊」，內容是依序的段落雜湊與使用的引擎。
  用來回答「這章是否已完整翻譯」、顯示標記與離線閱讀。作品與章節識別沿用同步已有的跨裝置
  識別，日後要讓譯文跟著同步或備份時不必改鍵。
- **漫畫分兩段存**：文字辨識結果以頁面圖片雜湊為鍵（下載清單已有每頁的 SHA-256），存文字框
  位置與原文；譯文再以「辨識結果＋引擎」為鍵。換翻譯引擎時不必重做辨識。
- **留存策略**：
  - 同一段可並存多個引擎的譯文，使用者選偏好的顯示。
  - 付費取得的譯文不會被免費機翻覆蓋，也不自動淘汰，只在使用者清除或移除作品時刪除。
  - 免費機翻的譯文設容量上限，超過時淘汰最久沒用的。
- 存在內容資料庫旁，另開資料表。只在本機，不同步。
- **備份**：由使用者選擇。建立備份時有兩個獨立的選項，「付費取得的譯文」與「免費機翻的譯文」；
  預設值為前者開、後者關（付費譯文重新取得要花錢，免費機翻可以重算）。選擇會記住，還原時
  備份裡有什麼就還原什麼。譯名表視為作品資料，一律隨備份。

### 4.3 譯名表

- 每部作品一份：人名、地名、專有名詞的固定譯法。
- 離線機翻：翻譯前後做替換。§3.5 的人名問題代表這對免費機翻是必要功能，所以放在階段 1。
- AI 供應商：隨提示詞送出。
- 譯名表改版只讓受影響的段落失效。

### 4.4 閱讀器呈現

- 小說：僅譯文、雙語對照、點段落切換三種模式；翻譯中串流顯示；一鍵切回原文。
- 朗讀可選原文或譯文（階段 2）。
- 漫畫：在原文區塊上鋪底放譯文，或點氣泡才顯示。
- 每部作品可各自設定是否翻譯、目標語言與偏好的供應商。

### 4.5 離線引擎的整合

- 以原生函式庫形式隨 App 建置，沿用 `sandbox-core` 的跨平台建置做法；來源釘到 commit，
  修補放在版本庫內。
- 模型不隨安裝包，按語言對下載，以登錄表的 SHA-256 驗證。
- 手機上單執行緒；一次只保留一個模型在記憶體，兩段式翻譯依序載入、用完釋放。
- 引擎本身約讓安裝包增加 10 MB（macOS 執行檔 9.6 MB）。
- 譯文做標點後處理（半形轉全形）。

## 5. 金鑰、隱私與費用

- 金鑰放現有的安全儲存（與 Proxy API 金鑰同一機制：Keychain／Keystore／DPAPI），不進備份與
  同步。其他翻譯設定可以跟著同步。
- 翻譯請求由 App 直接發出，不經過外掛沙箱；外掛讀不到金鑰與譯文。
- 專案的立場是本機優先、不做分析。離線引擎標示為「不外送內容」；啟用雲端供應商時明確告知
  閱讀內容會送到使用者選的第三方，並且必須由使用者主動開啟。
- 雲端供應商送出前顯示預估用量，可設每章與每日上限，超過即停。

## 6. 分期

| 階段 | 內容 | 完成的樣子 |
| --- | --- | --- |
| 0 | 引擎可行性驗證 | 已完成，見 §3 |
| 1 | 離線引擎與模型下載、供應商介面、翻譯記憶、小說三種顯示模式、譯名表 | 不填任何金鑰就能翻譯小說，重開不重翻，人名一致 |
| 2 | 自備金鑰的供應商（OpenAI 相容端點、DeepL）、費用上限、已下載章節批次預翻、朗讀譯文 | 願意付費的使用者可換成品質更好的引擎 |
| 3 | 漫畫：多模態 AI 整頁辨識加翻譯，覆蓋式顯示，辨識結果留存 | 填金鑰後可翻譯漫畫頁 |
| 4（不承諾） | 漫畫的裝置端文字辨識 | 漫畫也有免費選項；先實測直排日文的辨識效果，結果不好就不做 |

階段 1 的平台順序：桌面與 Android 先，iOS 隨後。iOS 真機已驗證可行，排後面只是因為它的建置
設定最多。

## 7. 風險與未驗證事項

- **中低階手機**：每個模型約 340 MB 的記憶體是固定成本。需要找一台中低階裝置實測，並決定
  記憶體不足時的行為（拒絕啟用，或只允許短段落）。
- **Windows**：離線引擎未試過。x86 是引擎的主要支援平台，預期風險較低，但未驗證。
- **修補的維護成本**：上游更新時 8 處修補都要重新確認。
- **離線機翻的品質**會決定第一版的口碑。緩解方式是譯名表、明確標示機器翻譯、一鍵切回原文。
- **整合後的行為未驗證**：階段 0 跑的是獨立程式，不是 App 內的函式庫。模型下載、背景執行、
  被系統回收記憶體時的行為都要在階段 1 處理。
- **漫畫的免費選項**取決於裝置端對直排日文的辨識效果，未驗證，可能做不成。在這個排序下，
  不付費的使用者暫時沒有漫畫翻譯。
- **iOS 27 SDK** 會終止沒有場景設定的 UIKit App。這只影響驗證用的獨立程式，正式整合是放進
  既有 App，不受影響。

## 8. 階段 0 若在其他裝置上結果不理想的退路

- 低階手機記憶體不足：兩段式翻譯分兩趟跑，每趟只載入一個模型（已是預設做法）；仍不足則該
  裝置只提供自備金鑰的供應商。
- 某個平台的建置卡關：該平台先只支援階段 2 的自備金鑰，其他平台照常出離線機翻。

## 9. 實作現況（v1.0.2-beta.1）

已實作：

- 離線引擎 `translation-core/`（Mozilla Translations／Marian，釘選 commit 與修補，見 `scripts/fetch-deps.sh`、`patches/`）：
  Android arm64 以 JNI 載入；iOS 靜態連結；macOS 與 Windows 為獨立的輔助程式 `shinsou-translate`。
- 模型依語言方向下載（8 個方向，全部以英文為中介），逐檔核對釘選的 SHA-256；載入前檢查可用記憶體，翻完一章即釋放。
- 翻譯記憶（§4.2）以內容雜湊為鍵；另外記錄每章用到哪些句子，使單章與單一作品的譯文可以刪除而不影響共用的句子。
  付費譯文不被免費譯文覆蓋，也不被自動淘汰。
- 譯名表（§4.3）：代碼保護；引擎遺失代碼的句子改以原文重翻。
- 自備金鑰的 DeepL 與 Google Cloud Translation（原訂階段 2，提前）：金鑰存於平台的安全儲存區，逐次請求計入每日字元上限。
- 自備的語言模型服務：OpenAI、Anthropic、Google Gemini 三種相容格式，位址、模型與金鑰由使用者填入（含本機或區網的模型伺服器）。
  每次送出最多 40 行連續原文並逐行編號，回傳的行號逐一核對；漏行、被輸出上限截斷的行留待重翻。譯文按格式、模型與位址分開保存。
- 閱讀器：頂列的翻譯按鈕、頁面上的狀態提示、僅譯文／對照／僅原文。設定頁：服務、金鑰、每日上限、模型、已翻譯章節清單與刪除。
- 備份：譯名表與每部作品的設定一律包含；已保存的譯文由使用者選擇，且只包含授權允許匯出的內容的譯文。

與原規劃不同或尚未完成：

- 內容授權沒有「匯出」權利（擴充來源的預設）的章節，仍可交給使用者自選並填金鑰的雲端服務翻譯（專案擁有者 2026-11-14 的決定）；
  這類章節的譯文不進備份。
- 「點段落切換」的顯示方式、邊翻邊顯示、EPUB 與漫畫翻譯尚未實作。
- Windows 的輔助程式只經過 CI 的自動化執行，未以人工驗證；Android 僅支援 arm64-v8a。
