# 漫畫翻譯：逐頁流水線評估（2026-11-16）

## 問題
閱讀時翻譯一話，要等到「整話辨識完 → 整話翻譯完」才畫出第一頁。能否改成辨識一頁、翻譯一頁、重繪一頁？

## 現況（`MangaTranslation.translateChapter`）
1. **辨識**：已經是串流——頁面依序載入、偵測，再分給多個 OCR 工作者；但要等全部頁讀完才進下一步。
2. **翻譯**：整話文字合成一份劇本（`MangaScript`），以一個 `ChapterTranslationRequest` 送出；`TranslationService` 內部再切成每次 48 行（語言模型約 40 行、兩個請求並行）。
3. **重繪**：拿到整話譯文才開始，每畫好一頁交給閱讀器一頁。

第一頁出現的時間 ≈ 整話辨識 + 整話翻譯 + 一頁重繪。

## 拆開後受影響的地方
| 項目 | 逐頁送的影響 |
|---|---|
| 翻譯記憶 | 逐行雜湊快取，逐頁送也能重用，**不受影響**。 |
| 整話紀錄 | 每次請求都會覆寫「這話用到哪些行」與完成狀態；需改成整話共用一個翻譯工作階段，最後才記錄。 |
| 計費（DeepL／Google／Azure） | 按字元計費，請求數變多**不增加費用**；但每次請求有 0.5～1.5 秒來回延遲。 |
| 語言模型 | 每次請求都重送系統提示（約 250 token），20 頁一話多約 5k 輸入 token；且只看得到一頁的幾行，**人稱、語氣、名字的一致性會變差**——提示詞本來就要求「連續數十行一起讀」。 |
| 離線引擎 | 目前每次請求結束就卸載模型（重新載入約 0.1 秒）；逐頁時應在整話期間保留模型。 |
| 預先翻譯佇列 | 只翻後面的章節、不需即時顯示，維持整話批次。 |
| 重繪快取 | 以「該頁譯文」為鍵；語言模型在不同上下文下譯文可能不同，快取會分開存，不影響正確性。 |

## 時間估算（依先前實測：每頁辨識約 0.3 秒吞吐、單頁從載入到辨識完約 0.6～0.9 秒、重繪約 0.2～0.5 秒；翻譯延遲為一般值）
以 Android SM-S9280、20 頁一話為例：

| 翻譯服務 | 現在：第一頁 | 嚴格逐頁：第一頁／整話 | 分段放大（1→2→4→8 頁）：第一頁／整話 |
|---|---|---|---|
| 離線引擎 | ~7 秒 | ~1.5 秒／~7 秒 | ~1.5 秒／~7 秒 |
| 雲端（DeepL 等） | ~8.5 秒 | ~2 秒／~15–20 秒（20 次來回，翻譯變瓶頸） | ~2 秒／~8–9 秒（約 5 次請求） |
| 語言模型 | ~20–45 秒 | ~5–10 秒／~60–150 秒，一致性變差 | ~5–10 秒／~25–50 秒 |

整話時間的瓶頸：辨識約 0.3 秒／頁，只要翻譯每頁平均不超過這個值，流水線就不會拖慢整話；雲端與語言模型的單次延遲遠超過，所以嚴格逐頁會讓整話變慢。

## 建議：分段放大的流水線
- 辨識照舊串流；譯文**依頁序分段**送出：第一段 1 頁（讓第一頁最快出現），之後 2、4、8 頁……，請求數約 log₂(頁數)。離線引擎與系統翻譯沒有來回延遲，可直接每頁一段。
- 每段譯文一回來就重繪、交給閱讀器，同時後面的頁繼續辨識、送下一段。
- 整話共用一個翻譯工作階段：翻譯記憶、整話紀錄、完成狀態、每日額度都照現在的語意，最後才記錄一次。
- 語言模型每段附上前一段的原文與譯文當作「只讀上下文」，保住一致性（多一點 token）。
- 閱讀器從中間頁開始讀時，可先處理目前所在頁附近（第二階段再做）。

## 工作量
- `TranslationService`：新增可分段呼叫的整話工作階段（保留現在的整段 API 給預先翻譯佇列）。
- `MangaTranslation.translateChapter`：把第 2、3 步改成依段循環；進度顯示改為「第 n 頁」。
- 語言模型提供者：支援只讀上下文。
- 測試：分段順序、整話紀錄只寫一次、取消與失敗時保留已翻譯部分、快取命中。
- 預估中等規模（約兩三個檔案的核心改動加測試），不影響桌機／iOS／Android 平台層。

## 實作與實測（2026-11-16）
- 設定「譯文 → 漫畫翻譯 → 閱讀時的翻譯方式」：**整話翻譯**（預設，原方案）或**分段流水線**。只影響正在閱讀的章節；預先翻譯的後續章節一律整話處理。
- 分段：1、2、4、8 頁（上限 8）；每段附前 30 行原文與譯文作為語言模型的只讀上下文；每段只存逐行翻譯（`ChapterTranslationRequest.segment`），全部完成後送一次整話請求（全數命中翻譯記憶）來寫整話紀錄。
- 開發者診斷新增「第一頁 n 秒」。
- 桌機實測（M4 Pro，21 頁，模擬雲端延遲：每次請求 0.8 秒＋每行 20 毫秒，已翻過的行不延遲；第 2 輪，模型已載入）：

| 方式 | 第一頁 | 整話 |
|---|---|---|
| 整話翻譯 | 3.7 秒 | 4.1 秒 |
| 分段流水線 | 1.3 秒 | 5.7 秒 |

  整話多出的時間來自分段請求依序來回（約 5 次）。手機辨識較慢、與翻譯重疊更多，差距預期更小。若要再縮短，可讓下一段在上一段譯文回來前就送出（代價是少了上一段的上下文）。
